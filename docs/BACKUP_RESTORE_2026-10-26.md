## Implemented tools

- `scripts/backup-db.mjs` streams a PostgreSQL custom-format dump directly into AES-256-GCM encryption. No plaintext dump is written. A separately supplied 32-byte random key is read from `BRILJANTE_BACKUP_KEY`, never printed or passed in arguments. The encrypted archive and checksum manifest must be outside the repository; the output directory is restricted to the current user on Windows.
- `scripts/restore-db.mjs` authenticates the entire encrypted archive before writing. It permits only a new, empty, local `briljante_restore_*` database with an explicit disposable-target flag. Remote restoration is refused. Restore is one transaction, preserves ACL/RLS/function definitions and refuses nonempty databases.
- `scripts/backup-rehearsal.mjs` creates a fresh loopback-only PostgreSQL cluster, applies every migration, builds fictional records, runs acceptance, encrypts/restores/verifies, then stops and removes its own synthetic cluster. It creates no Windows service, remote project, provider payment or email.
- `scripts/backup-common.mjs` supplies shared project/TLS/target/path guards and encrypted archive handling. No passwords, keys or database URLs are stored in these files.

## Hosted backup prerequisites and recovery boundary

No hosted backup was downloaded or restored. Root can inspect the existing dedicated project dashboard without resetting a password. Actual logical backup requires all of the following:

1. PostgreSQL direct or **session** pooler access to `cigyxjfzbjlgbrduzcpw`, using the existing database password supplied securely through a restricted `PGPASSFILE`; a Supabase HTTP service key cannot replace it. Do not reset an unknown password for this rehearsal.
2. Matching-major PostgreSQL tools; `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGSSLMODE=verify-full`, and the approved `PGSSLROOTCERT`. Remote backup additionally requires `BRILJANTE_BACKUP_PROJECT_REF=cigyxjfzbjlgbrduzcpw`. The helper rejects other projects and refuses `PGPASSWORD` for remote work.
3. A private backup destination outside Git/public output and a random `BRILJANTE_BACKUP_KEY` retrieved from a secure store. Keep the key separately recoverable; loss of the key makes the archive unusable. Neither the key nor `PGPASSFILE` belongs in a committed environment file or command argument.
4. An actual backup run followed by a separately isolated, compatible recovery exercise. The local restore helper intentionally cannot restore over the hosted project. Full hosted recovery must follow the current Supabase procedure, including managed roles/extensions and Auth/Vault/encryption-root requirements where applicable.

