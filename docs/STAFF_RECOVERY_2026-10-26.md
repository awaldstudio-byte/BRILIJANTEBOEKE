# Staff password recovery

Implemented locally on 26 October 2026. Provider acceptance and hosted release remain pending. No schema change, real password change, real authenticator code, outbound authentication email or client invitation was used for this work.

## Account flow

The sign-in screen offers Forgot password in English and Afrikaans. The recovery request returns the same message and opaque, 15-minute browser challenge cookie for configured, unknown, inactive and first-time addresses. Only an individually preapproved, active staff identity with an existing password is queued for recovery mail. The existing email-first approval-routing endpoint is retained; this change does not claim that endpoint hides approval status.

Setup and recovery share the same database-backed quotas: 60 requests per IP per 15 minutes, 10 code requests per IP and 3 per email per 15 minutes, and 50 outbound-code requests globally per hour. Rate-limit identifiers are hashed. Same-origin checks remain required.

Existing accounts use Supabase recovery OTPs; first-time setup uses the existing email OTP. Codes are generated by the provider and delivered with the approved branded message and inline logo. The application stores no code, password or authenticator secret. The browser challenge expires after 15 minutes, permits at most five verification attempts and is consumed once. An expired, exhausted or used challenge clears its browser cookie.

Mailbox verification creates only a short verified stage. If an authenticator is already enrolled, its existing code is required before password selection. Recovery cannot skip, enroll, remove or replace that factor, and successful recovery MFA does not grant dashboard access. Fresh provider identity and factors are checked again when changing the password.

The verified stage is consumed atomically before credential mutation. All other application sessions for the same user are revoked, other provider sessions are signed out, and the password is changed through user-scoped updateUser. A new 15-minute password-stage session is issued only after every required step succeeds. Failure leaves no usable replacement application session; the user requests a new email code. Previously enrolled MFA remains required. Revoked provider JWTs may exist until expiry, but revoked application-session records block their use against staff APIs.

## Lost authenticator

The screen directs the user to technical support for independent identity verification and tells them never to send a password, code or setup key. Email verification alone cannot remove an enabled factor. There is no application endpoint that bypasses or deletes an enrolled authenticator. Any provider-owner recovery requires a separately verified human process and remains outside this self-service flow. No lost-authenticator account change was performed or claimed.
